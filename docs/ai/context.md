# AI Project Context

This file gives future AI-assisted sessions a short, durable project snapshot. Keep it current when major architecture or product decisions change.

## Product

EVMWhaleTracker is a .NET 10 Telegram bot for tracking on-chain wallet activity on EVM-compatible chains. The current MVP is focused on ERC-20/BEP-20 token transfer notifications for tracked wallets.

## Current Runtime Shape

Configuration separation is implemented pending independent review and local rollout; see [the plan](../plans/configuration-secrets-separation.md) and [operator guide](../operations/configuration.md). Public defaults and Development logging live in appsettings; optional ignored `appsettings.Local.json` holds private deployment settings and is mounted read-only by Compose. Credential-only User Secrets, canonical dotenv environment keys and explicit command-line overrides follow in precedence order. Stale nonsecret User Secrets are ignored. The migration preserves the running DB connection, Hyperliquid/Polymarket settings and disabled billing flags before credential regeneration. Local settings and validation artifacts are excluded from images and publishing. No database migration or live acceptance is implied by this refactor.

Local recovery on 2026-10-23 restored a stopped PostgreSQL container and the bot, which had failed startup migrations while the database hostname was unavailable. Both Compose services now use `restart: unless-stopped`; start the full stack with `docker compose up -d --build` to honor database health gating. Wallets and Hyperliquid settings were preserved, all live subscriptions reconnected, and Telegram `/list` responded. Hyperliquid history-completeness warnings remain after downtime. See the [recovery record](../plans/postgres-restart-recovery.md); the policy does not provide uptime while Docker/the computer is off.

- PostgreSQL stores user and tracked-wallet configuration.
- `TrackedWalletCacheHydrationService` loads tracked wallets into an in-memory cache.
- `TokenTransferLogSubscriberWorker` opens websocket log subscriptions for ERC-20 `Transfer` events where tracked wallets appear in indexed `from` or `to` topics.
- `WalletTrackerWorker` consumes pipeline messages, applies tracked-wallet settings, resolves token metadata and USD value, and writes structured notification payloads.
- `NotificationDispatcherWorker` sends Telegram messages with rate limiting.

Native transfer tracking is currently disabled at runtime. The native block-scanning code remains available through `NethereumBlockchainBlockSource` and `BlockchainIndexerWorker`, but those services are not registered in the active host configuration.

## Important Constraints

Runtime errors, messages and semantic string tokens use named catalogs; see [conventions](conventions.md#named-errors-and-runtime-strings) and the [refactor record](../plans/named-errors-and-string-catalogs.md). Domain's `Errors` catalog owns entity/value-object invariants. Application owns use-case/port catalogs (`PolymarketErrors`, `HyperliquidErrors`, `AssetPriceErrors`, `TokenMetadataErrors`), while Infrastructure owns adapter-specific seed-import errors; see [error ownership](../plans/error-catalog-layer-ownership.md). Presentation copy stays in Telegram text catalogs, and persisted/protocol/callback values retain their existing representation. This structural cleanup does not change database schema or tracking behavior.

- Do not reintroduce per-transaction receipt fetching for token detection.
- Do not poll `eth_getLogs` per block for quiet wallets.
- Prefer websocket log subscriptions for token transfers.
- Keep caching in-memory for the MVP; do not add Redis.
- Preserve the Domain/Application/Infrastructure/Presentation layering.
- Expected business-flow failures should use the `Result` pattern instead of exceptions.

## Current Tradeoffs

- Token tracking is cheap and event-driven because ERC-20 transfers emit indexed logs.
- Native transfer tracking requires block scanning with standard EVM RPC, so it is disabled for now to reduce API usage.
- Native tracking can be re-enabled later if API budget or product requirements justify it.


## Polymarket prediction tracking

Polymarket profile lookup and prediction tracking are implemented and deployed locally. The [completed Polygon brief and live rollout](../plans/polymarket-polygon-tracking-implementation-brief.md) supersede the original activity-polling design. A dedicated Infura Polygon adapter uses filtered settlement logs, rich durable identities, finalized-block processing, bounded reconnect recovery, cached Gamma market enrichment and an owner/generation-scoped outbox sharing Telegram limits. Current/historical own-maker fills use pinned ABI families; direct CTF and official AutoRedeemer aggregate payouts are supported. Ambiguous generic routes, combos, perps and interpreted position-open/close labels remain excluded. See the [contract/evidence record](../plans/polymarket-polygon-contract-registry.md).

Private local settings `Polymarket:Enabled=true` and `PolymarketPolygon:Enabled=true` enable the services; checked-in defaults and each wallet's tracking preference remain off. Polygon was enabled by the user in the existing Infura project. The user's desktop VPN restored trusted API access; do not bypass TLS validation. Profile suggestions, custom aliases, account confirmation and independent gross-collateral thresholds were live-tested.

On 2026-10-25, real natural prediction BUY alerts matched public API and durable raw-log evidence. A high-minimum temporary enrollment verified suppression and returned to Active after deliberate restart; canonical duplicate checks passed. Both temporary entries were removed, with original wallet/Hyperliquid/Polymarket preferences preserved exactly and no queued test deliveries left. Initial HTTP 429 exposed a recovery burst; shared pacing/cooldown now separates throttling from adaptive range splitting. Fresh integration and independent review/fallback verification completed. No mocked suite was run. Live SELL/redemption, actual reorg correction, multi-owner races and outage scenarios remain unexercised; latency was not benchmarked and high-volume recipients can build a backlog. Public mapping is working and does not require ownership verification.
