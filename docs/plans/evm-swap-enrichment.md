# EVM swap notifications without native block scanning

- Status: completed (implementation; rollout blocked by provider qualification)
- Date: 2026-10-30
- Summary: retain wallet-filtered Transfer subscriptions, enrich only matching transactions, and render verified swaps as one notification. Native block scanning remains disabled.

## Problem and reference

The current pipeline reports token transfer legs rather than interpreted trades. In the inspected [Ethereum transaction](https://etherscan.io/tx/0xeb2fb8b3a577fd9d4dd71d70e80b46c0c9e4b5288cb536e6196a42ed8ad6c697), the tracked wallet sent 115,160.747406552094646927 ONDO to a Uniswap V3 pool and received 17.721444116587579749 native ETH internally from the router. Pool-to-router WETH and its unwrapping did not involve the tracked wallet in ERC-20 Transfer topics. The top-level transaction value was zero. Our outgoing ONDO alert and Drops Bot's ONDO-to-ETH swap alert link to the same transaction.

This feature follows the completed [notification enrichment plan](notification-enrichment-implementation-plan.md); it does not activate its deferred native scanner. Implementation was authorized on 2026-10-30 for Ethereum Uniswap V3 first, with other chains retaining transfer fallback. Deployment, provider purchases, production migrations and live Telegram validation are excluded from that authorization.

The generated additive migration is `20261030114534_AddSwapDecisions`; startup applies migrations before hosted workers. Pending work is not pruned; terminal identities expire seven days after intake. Disablement resolves undecided work to ordinary permitted transfers and keeps retained identities authoritative over ordinary replay. Do not drop the table during operational rollback: doing so loses replay protection.

Integration fixes bind trace-root calldata to the transaction, normalize source hashes, preserve repeated identical transfer legs, bound metadata/pricing waits, and validate canonical block time even when tracing is unavailable. A fallback whose canonical inclusion time cannot be established within its preparation budget is suppressed; an observation timestamp cannot stand in for activation time. Activity predating the wallet generation is rejected. Restart-expired jobs get a bounded fallback preparation window and never restart tracing. The EVM dispatcher uses a dedicated Telegram client with internal retries disabled, so its explicit retry policy repeats all current ownership/settings/access checks before every physical send. Other Telegram clients and Hyperliquid/Polymarket/billing transports retain their existing configuration.

## Product scope

First release: Ethereum mainnet, validated Uniswap V3 pools and explicitly supported router versions, for simple swaps whose evidence shows exactly one net asset spent and one net asset received by the tracked wallet. Support token/token, token/native ETH and native ETH/token when an existing wallet-visible token Transfer triggers detection. Include supported multihop paths only when all hops and wallet accounting can be verified; ambiguous split routes initially fall back.

Other chains continue existing alerts. Later expansion requires a provider capability check and a chain-specific registry/test corpus; do not assume Ethereum tracing support applies to BSC, Base, Arbitrum or Robinhood.

Exclude native-only sends/receipts without a token trigger, bridge interpretation, liquidity additions/removals, lending, arbitrary aggregators/routers, universal decoding, account-abstraction bundles, fee/rebasing-token interpretation, swaps with several net input/output assets, historical replay, and changing paywalls. Hyperliquid and Polymarket remain separate and unchanged. A token named ETH/WETH or a counterparty label never proves a swap.

Target presentation, using existing explorer links, alias and edit navigation:

```text
<wallet alias> | ETH | <edit>
🔀 Swapped 115,160.75 ONDO for 17.721444 ETH via Uniswap V3
<Tx hash>
```

Only verified protocol identity earns the protocol label. Optional USD value is a quoted input-side estimate, not actual execution price or P&L. Never display both input and output USD values as additive turnover. If useful, an execution ratio must be derived from the actual token amounts with an explicit unit; omit it initially to keep the message compact.

| Area | Current behavior | Planned responsibility |
| --- | --- | --- |
| `Program.cs` | Registers Transfer subscriber, wallet matching, aggregation and dispatcher; no native scanner | Register default-off bounded enrichment workers and provider adapters |
| `TokenTransferLogSubscriberWorker` / `RawLogData` | Wallet-topic subscriptions; transaction list empty; raw adaptation drops log index/removed state and uses receive time | Retain source block hash, transaction hash, log index, removed flag and observation time explicitly |

| `NotificationAggregationWorker` | Sliding one-second quiet timer; appends transfer lines | One terminal swap-or-transfer decision for enrichment candidates, using full transaction evidence and a fixed maximum wait |

| Dispatcher / billing access | Shared delivery limits and access checks | Recheck current wallet, networks, directions, filters and access before send; do not bypass delivery controls |

Do not place RPC tracing inside the Telegram renderer or single sequential dispatcher loop. Do not treat the existing debounce as transaction completion. Do not add Swap to a single-asset transfer record without representing both sides.

## Provider qualification before implementation enablement

Implement an Application port such as `ITransactionExecutionEvidenceProvider`, with Infrastructure adapters and named Result errors. Evidence must provide transaction success, original sender/destination/value, complete receipt logs and successful native execution movements, including reverted-ancestor exclusion. Receipt, transaction and trace must refer to the same chain, hash and canonical block hash. Retain raw integer units (`BigInteger`) and token decimals; convert for display only at a checked boundary.

Preferred qualification candidate: existing Infura/MetaMask Ethereum [`trace_transaction`](https://docs.infura.io/reference/ethereum/json-rpc-methods/trace-methods/trace_transaction/), subject to account entitlement and actual endpoint availability. The documented flat trace includes call hierarchy through `traceAddress`; reject reverted descendants as well as failed frames. `debug_traceTransaction` with a full [Geth call tracer](https://geth.ethereum.org/docs/developers/evm-tracing/built-in-tracers) is an alternative only after endpoint support is confirmed; `onlyTopCall` cannot supply internal movements. Choose one qualified method, with no automatic method-guessing cascade. A decoded indexer is an alternative only if it exposes equally verifiable asset movements and completeness; a human-readable swap label alone is insufficient. Use the smallest supported combination of transaction, receipt and trace requests; do not fetch redundant data already included in a response.

Provider constraint checked 2026-10-30: Infura [lists Debug/Trace API under Developer at USD50/month and above](https://www.infura.io/pricing). We have not checked this account's entitlement and must not assume its existing key permits tracing. The [published credit table](https://docs.infura.io/get-started/pricing/credit-cost/) lists Ethereum trace_transaction at 300 credits, debug_traceTransaction at 1,000 and transaction/receipt reads at 80 each. An illustrative transaction+receipt+trace_transaction bundle is 460 credits per unique matching transaction before metadata, registry, canonicality, retries or existing WebSocket costs. Reconfirm at implementation time. These figures do not promise that every chain supports the methods or that an upgrade is necessary for this specific account.

Before rollout, use read-only requests for the known transaction to establish actual available methods, receipt/trace block binding, historical reach, response limits, timeout behavior and provider billing units. Inspect current official documentation and the account's supported API configuration without printing credentials. Unknown capability means that chain stays disabled; it does not authorize buying an upgrade or silently changing providers. Document a provider request/CU budget using measured responses, not a promise of free tracing.

This is an explicit proposed exception for **targeted transaction enrichment**, not a return to receipt-based token detection. Detection remains WebSocket logs. No per-block `eth_getLogs`, full-block scanner or unrelated transaction inspection. Implementing/activating this plan must preserve that scope in repository instructions/docs.

## Processing design

1. **Candidate intake:** wallet-visible Transfer logs for an enabled chain create a transaction candidate before price/minimum filtering. Reject malformed identities. Persist enough identity for removal/replay handling and preserve the raw baseline transfer observations. Deduplicate logs by chain, block hash, transaction hash and log index. Do not let the current subscriber dedup hide removed notifications.
2. **Public evidence sharing:** combine simultaneous requests for `(chain, transaction hash, block hash)` into one in-flight fetch. Cache only public execution evidence with bounded TTL/size. Never cache recipient aliases, thresholds, settings, access decisions or rendered messages globally. Provider work is independent of the number of recipients.
3. **Budgeted enrichment:** initial proposed limits are four concurrent transaction jobs per process, a 256-job enrichment admission limit, provider-specific pacing/circuit breaker, and a three-second maximum decision wait from the first candidate. These are configurable tuning defaults, not measured latency guarantees. Include queue time and all retries inside the deadline. When enrichment admission is full, atomically choose fallback without waiting for a trace slot. Persist the decision/outbox before attempting bounded delivery-channel writes; a full delivery channel leaves it pending for a paced outbox drain rather than creating another task. Initially cap unsent durable work at 10,000 recipient decisions per chain. At that cap or database unavailability, stop admitting work for that chain and apply bounded intake backpressure; ordinary alerts on the affected chain can consequently be delayed. Other chains use separate intake/admission quotas. Do not promise lossless, nonblocking behavior under unlimited overload. Bound the subscriber's currently unbounded per-connection ingress (initial 512 logs); overflow must mark the source degraded, emit an explicit possible-gap diagnostic and disconnect with cooldown rather than silently drop or grow memory. Existing EVM ingestion has no durable reconnect backfill guarantee, and this feature does not invent one. Already persisted decisions survive pressure; unadmitted events during an ingestion gap cannot be promised. No raw subscriber waits specifically for tracing and no unbounded Task-per-wallet/log is allowed.
4. **Evidence verification:** confirm successful canonical execution and match the triggering log to the full receipt. Where a trace omits block identity, bracket the fetch with receipt/canonical-header checks and require the same canonical inclusion before and after; cache evidence only under that verified block version. Missing or inconsistent data, oversized/truncated traces, unsupported calls or response limits cause fallback. Pending/unavailable evidence may be retried once within the original deadline; unsupported methods must not cause retry storms. Honor 429 Retry-After/cooldown; provider backoff must not occupy ordinary-alert dispatch workers.
5. **Wallet accounting:** derive signed net movements of each ERC-20 and native asset for each tracked wallet from complete logs/calls. Remove gas costs, unwrap/wrap bookkeeping, self-transfers and refunded unused native input from traded amounts. Exclude reverted calls and their descendants, delegatecall value duplication and duplicate trace nodes. Keep actual wallet debit/credit separate from pool hop quantities.
6. **Protocol proof:** decode pinned Uniswap V3 [Swap events](https://github.com/Uniswap/v3-core/blob/main/contracts/interfaces/pool/IUniswapV3PoolEvents.sol) and supported router execution. Validate pool identity using chain-specific deployment/[factory getPool](https://github.com/Uniswap/v3-core/blob/main/contracts/interfaces/IUniswapV3Factory.sol) equality and token pair/fee evidence, caching verified registry data. Verify the complete successful path and reconcile its input/output to wallet movements. A Swap-signature lookalike, router destination, outgoing token plus unrelated ETH refund, or WETH Withdrawal alone is insufficient. Explicitly distinguish [unwrapWETH9 and refundETH](https://github.com/Uniswap/v3-periphery/blob/main/contracts/base/PeripheryPayments.sol). Do not trust token symbols, address labels or unchecked decoded provider strings.
7. **Per-recipient policy:** on a verified swap, aggregate same-asset input/output legs before checking the wallet USD minimum. Use the spent asset's existing price provider and inclusive minimum; a positive minimum with unresolved input valuation suppresses, while zero allows an amount-only swap. Do not infer USD price from the trade itself or weaken the unpriced filter. A swap requires both direction/token preferences to permit its visible legs; otherwise use only ordinary permitted transfer lines. Re-read settings/access before final delivery. For fallback, preserve existing per-leg threshold and direction semantics exactly; do not manufacture a larger aggregate USD value.
8. **One terminal decision:** publish either one swap or the collected permitted transfer lines for that recipient/wallet/transaction. The fixed deadline never slides on new logs. Late enrichment cannot publish a second alert or edit a transfer into a swap. Cancel abandoned fetches when possible, but one cancelled recipient must not cancel shared work still needed by others. Empty/suppressed outcomes are terminal too.

Complete receipt evidence is the source for classified swaps; the single wallet log cannot establish their full amounts. Fallback remains honest about known transfer legs and does not claim complete transaction interpretation. Handle later same-transaction logs through the decision record, not by starting another timer. Document that a deadline fallback can omit late legs rather than promise completeness without evidence.

## Persistence, duplicate delivery and reorg boundaries

Use PostgreSQL for a small durable candidate/recipient-decision/outbox record for the enabled enrichment path, with unique identities and atomic decision-to-outbox transition. Share public evidence with in-memory caching, not Redis. Existing unrelated notification paths need no new durability promise.

Separate logical notification identity `(chain, transaction hash, user, tracked-wallet ID, activation generation)` from block-version evidence `(block hash, log index)`. Store entitlement revision/valid-until and relevant wallet settings revision with the work; stale generations are cancelled. Worker leases prevent two hosts from deciding the same job. Ordinary restart/reconnect must not create another swap/transfer for an already decided transaction; disabling the feature must drain pending jobs to fallback while keeping decision identities. Define retention/replay horizon explicitly (initial seven days), and never claim dedup beyond it.

Removed logs/canonical-block mismatch invalidate evidence and unsent work. If the same transaction is re-included, classify its new block version only if no alert was sent; do not double-notify a sent logical identity. A sent alert invalidated by a reorg should have an invalidated status in diagnostics; automatic correction messages are deferred. This retains low-confirmation alert risk and does not promise finalized execution. Log observation time is not block time; retrieve/cache real block timestamps where required for activation comparisons.

Transactional decisions prevent application-generated duplicate swap/fallback decisions. Telegram accepted-send/crash ambiguity can still repeat a message; do not claim exactly-once Telegram delivery. At shutdown use a bounded drain/persist strategy rather than waiting indefinitely for a provider. Schema changes must be generated with EF tooling; record migration/retention/rollback behavior.

## Configuration, privacy and metrics

Add default-off `SwapEnrichment` options in appsettings: enabled chains, supported protocol registry version, total deadline, concurrency/admission/cache limits, cooldowns and retention. Keep API credentials/provider URLs containing keys in User Secrets/environment. Preserve billing sandbox's zero-tracking isolation. No user tier changes or new command is required.

Record classified/fallback/suppressed counts and reasons, queue age, provider latency, API calls/CU where exposed, coalescing/cache hits, 429s, mismatched evidence and invalidated blocks. Avoid tokens, credential-bearing URLs, raw user messages or unbounded full traces in logs. User-facing fallback keeps the current transfer layout; technical failure details belong in diagnostics. Domain owns no provider-specific error catalog.

## Implementation stages and exit criteria

1. **Qualify provider and contract registry:** document actual method support and costs for Ethereum; validate the reference transaction and pinned supported routers/pools against primary sources. Exit: verifiable complete evidence or an explicit provider blocker, without changing running tracking.
2. **Application contracts and persistence:** typed evidence/swap/decision outcomes, named errors, log identities, durable decision/outbox and bounded channels. Add migrations only through EF tooling. Exit: source/recipient isolation, replay and expiry contracts covered.
3. **Infrastructure enrichment and classification:** provider adapter, coalescing, budgets/cache, canonical verification, Uniswap V3 decoder and wallet movement accounting. Exit: known positive and negative transaction corpus passes.
4. **Pipeline/presentation integration:** pre-filter candidate routing, atomic swap/fallback selection, pricing/preferences/access checks, compact renderer and shared Telegram limits. Feature off must reproduce the old path. No native scanner registration changes.
5. **Fresh integration and independent review:** use the required one-writer development workflow; review completeness, precision, spoof/revert cases, lifecycle and access ownership. Resolve findings through the sole writer.
6. **Validation and controlled rollout:** focused tests; full solution tests after any EF migration; synthetic export/Compose and fresh database/upgrade checks. Author a manually invoked live swap runbook. Historical public transaction replay proves decoding only, never fresh Telegram delivery. Enable only the qualified Ethereum adapter after an explicitly requested rollout; bounded natural-event validation then restores temporary enrollments/settings. No trades or funds required. Stop after one verified swap, one fallback or ten minutes; missing natural activity is inconclusive. Measure added latency/request volume before enabling further chains. Rollback turns enrichment off and safely resolves admitted work to fallback.
