# Polymarket provider budget

Status: completed
Date: 2026-11-04
Summary: Replace continuous Polygon heads with event-driven finality work, sparse canonical maintenance and bounded coverage audits after the shared Infura project exhausted its daily allowance. Implemented, freshly integrated, independently reviewed and deployed locally; healthy-provider live acceptance remains blocked.

## Requirements and scope

Keep the five existing wallet-filtered log subscriptions and remove `newHeads`. An independent ordered queue reader persists logs/removals and acknowledges durability barriers while the RPC scheduler works. Existing canonical commit/removal locks remain: persistence can briefly wait for a fresh canonical commit check, but never runs a complete finality pass itself. Retain durable identities, removed-log correction, finalized boundaries, fresh pre-commit canonical checks, recipient ownership/generation, billing eligibility and bounded channels. No long-lived canonical block cache, receipts, native scanner, Redis or changes to other chain/billing/Hyperliquid adapters. No migration or new mandatory DI registration.

Pending/Enriching raw rows for active source topics drive retries. Validate only active checkpoints during steady state, and freshly validate the complete desired source set before recovery, including reactivated sources. Inactive historical inbox rows must not drive fast retries or fallback normalization work. Account-set changes continue to rebuild subscriptions/recover promptly.

A timer plus a local queue barrier cannot prove that all filtered socket frames through an HTTP head have arrived. Consequently normal finality/maintenance never advances durable coverage. The coordinator explicitly authorized a sparse coverage audit: query all five existing filters from the last proven cursor to a finalized boundary, capture the canonical range anchor before querying, persist every filter result, await the ordered queue barrier, freshly revalidate the prior active checkpoint proof and range anchor under the canonical commit lock, then advance coverage. Any changed proof refuses the range; checkpoint rewinds are committed before recovery restarts. This is a five-minute catch-up audit, distinct from prohibited per-block quiet-wallet polling. Reconnect recovery retains the same barrier requirement. Partial failed ranges never advance coverage; adaptive splitting is only for range/response limits, with finite recovery request budgets.

## Defaults and explicit budgets

| Setting | Default | Behavior |
| --- | --- | --- |
| PendingRetrySeconds | 2 | Minimum interval after a finality pass finishes; serialized, no overlapping finality passes |
| MaintenanceSeconds | 120 | Active canonical checkpoint validation and pruning while quiet |
| CoverageAuditSeconds | 300 | Bounded five-filter audit to consensus-finalized boundary |
| DailyHttpRequestLimit | 12000 | Process-local UTC-day attempted HTTP request cap, shared by this Polygon RPC singleton |
| DailySocketMessageLimit | 10000 | Process-local UTC-day received JSON message cap; pauses ingestion until reset if exceeded |
| RpcMinimumIntervalMilliseconds | 250 | Existing HTTP pacing; log queries impose at least one second |
| RecoveryRequests | 200 | Existing finite request budget per recovery/audit invocation |
| KeepAliveInterval / KeepAliveTimeout | 20s / 20s | Transport PING/PONG liveness, no billable head subscription |

For one distinct active covered checkpoint, quiet maintenance normally needs three reads every 120 seconds (latest, finalized, checkpoint): about 2160 reads/day. With finalized Polygon blocks fitting one configured 1000-block range per five-minute audit, audits add five log queries and six reads per audit (latest, finalized, prior-proof validation, range anchor, commit-time prior-proof validation and fresh anchor): about 1440 log queries plus 1728 reads/day. At the documented 80 credits per block-number/block read and 255 per log query, this baseline is approximately 678240 credits/day (5328 HTTP calls including 1440 log queries), excluding socket deliveries. See [Infura credit costs](https://docs.infura.io/get-started/pricing/credit-cost/). Multiple distinct checkpoint heights add one read each per maintenance; validation shares identical heights only within a single call. Startup, reorg ancestry, source changes, pending normalization and retries add bounded work. At most 12000 attempted HTTP requests/day are admitted in one uninterrupted process. High volume reaches this cap and pauses rather than silently sustaining unlimited HTTP consumption.

These are request bounds, **not a project-wide daily-credit guarantee**: Infura method/delivery pricing, other adapters sharing the project, restarts, multiple owners/processes and socket messages already delivered before the cap all matter. Counters/caps reset on process restart; they are deliberately not advertised as durable accounting. Socket deliveries already incurred cannot be uncharged; hitting the cap can produce degraded coverage/recovery work. Monitor the actual provider dashboard and request summaries. No claim that the full shared account stays below three million daily credits is established.

Daily HTTP 402 / RPC 402 or -33000 errors pause until 00:00 UTC. HTTP 429 honors bounded explicit Retry-After (1–60 seconds); without that header, consecutive HTTP 429 responses back off 10, 20, 40, 80, 160 and 300 seconds, capped at 300 until a healthy RPC response resets the sequence. RPC 429/-33200 uses a bounded cooldown; quota classification precedes WebSocket chain-ID validation. Range code -32005 alone is not a quota error. HTTP and socket owner paths share the options-instance cooldown. Cooldown refusals occur outside the per-request timeout and issue no network request. Other owner failures use bounded exponential reconnect delay (up to 300 seconds). Cancellation interrupts waits. Diagnostics exclude arbitrary provider messages and endpoint/key text. Request summaries expose attempted HTTP/log totals and today's received socket count, including on failed reconnects.

Quiet sockets use transport heartbeat instead of a 90-second data-arrival deadline. Continuous queue pressure can delay an outstanding ReceiveAsync; bounded queue and transport timeout remain deliberate safety limits, so sustained overload may reconnect/recover. Natural trading latency target remains approximately 5–10 seconds after finalization when provider/enrichment/queue work is healthy; no live numeric guarantee has been established.
